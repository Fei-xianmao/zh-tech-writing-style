# 语言与结构

对应原指南第 2、3、6、7、8 章。数字限制是原指南的写作建议，不是自动判错阈值。具体数值和标点另见[数字、单位与标点](numbers-and-punctuation.md)。

## 语言风格与用词

依据：§2.1～§2.6。

- 对话式表达指自然、直接，如“你可以……”，不等于照录松散口语。客观传达信息，避免产品推销、过度拟人、玩笑、反问和不必要的感叹。
- 不轻易使用“请”“抱歉”，避免“亲爱的”等过分亲切的称呼。全文统一“你”或“您”；需要指称作者时优先用“作者”，少用“我”“我们”。
- 删除不增加信息的字词与重复说明，优先主动表达。不要为避免被动句而改变责任主体或事实。
- 使用读者能理解的现代汉语。将“CPU 打到 60%”写成“CPU 使用率达到 60%”，将只有行业内部才懂的简称展开。
- 避免侮辱性称呼、脏话、谐音错别字和无依据的“最佳”“最先进”等评价。涉及地区、机构或品牌时使用准确、适当的名称，不自行创造称呼。
- 区分“的、地、得”；“其、该、此、这”必须指向明确。同一对象、动作、参数说明和引导用语尽量保持一致。
- 用已知数据、实例和条件替代“很多”“很好”“数倍”等模糊描述。没有证据时标明待确认内容，不将不确定的事实改写成确定结论。

示例：

> 原文：将其 `image` 字段留空。
>
> 改写：将相应镜像的 `image` 字段留空。

只有上下文能确定“相应镜像”时才能这样改写；否则先确认代词指向。

## 标题与目录

依据：§3.1、§3.4。

- 原指南将文章标题到正文小节分为最多 4 个逻辑层级，禁止跳级；通常建议控制在 3 级。平台自动生成文章标题时，正文从平台约定的层级开始，不机械补 `#`。
- 标题概括本节中心内容，简短明确；同级标题尽量采用相同结构。操作任务优先用“配置 MySQL 数据库”这类“动词＋对象”标题。
- 不在标题中解释缩略语，通常不用句末标点；下级标题不重复上级标题，不产生只有一个同级小节的孤立层级。
- 标题下先有必要的介绍或正文，再进入下级标题。短小的并列项通常用列表，不为每项增加标题；列表项内部不嵌套标题。
- 一本技术手册提供涵盖章节及附录的总目录；图表较多的安装手册可按发布要求提供图目录和表目录。网站使用全站与页内导航实现相同目的。
- 根据当前文档框架实际检查目录和锚点，不把原指南中的某个框架版本示例当作今天所有框架的限制。

## 段落与句子

依据：§3.2～§3.3。

- 每段一个主题，核心句通常放在段首，后续句子提供依据、条件或解释。
- 原指南建议每段约 50～200 字，尽量不超过 250 字；每句建议不超过 100 字。用于发现拥挤、冗长的表达，不用于给短文补字或机械拆句。
- 拆开连续多层修饰和“一逗到底”的句子；用简单句或并列句清楚表达因果、条件和顺序。拆句后重新检查主语与代词。
- 正文通常顶格，不用空格模拟首行缩进。段间保留适当间距，采用平静的陈述语气。
- 复杂技术关系、对比或流程适合图表时，考虑先给图表再解释；不为简单信息强行增加图表。

## 名称、术语和文件名

依据：§6.1～§6.3、§7.1、§8。

| 对象 | 默认处理 |
| --- | --- |
| 产品、公司和品牌 | 使用官方名称与大小写，如 MySQL、GitHub、WeChat；不照搬历史品牌列表 |
| 官方中文名称 | 读者熟知时直接使用；不熟悉时首次给“中文名称 (Official Name)”，之后统一中文名称 |
| 没有官方中文名称的产品 | 保留官方英文名称，不自造译名 |
| 中文句子里的普通英文词组 | 保持普通小写；专有名词保留官方大小写，完整英文句子保留其首字母大写 |
| 新建普通文档源文件 | 名称简短、能概括内容；默认小写英文单词，以 `-` 连接，如 `install-mysql.md` |
| 文件扩展名 | 默认小写 `.md`；项目统一使用 `.markdown` 时沿用既有约定 |
| 固定入口及既有文件 | `README.md`、`SKILL.md` 等按工具约定；不为风格擅自重命名既有文件、路径或链接 |
| 系列文档 | 统一维护术语和缩略语；适合时提供术语表、缩略语表及必要的商标与来源说明 |

新建文档文件名不建议使用下划线，不混用大小写。产品命名属于公司的命名流程；普通文档润色不扩大为品牌重新命名。

## 拼写与语法检查

依据：§7.1～§7.3。

- 同一文档保持选定的简繁体；代码、引文及名称保留原样。
- 检查中英文错字、近形词和近义概念。`authentication` 与 `authorization` 的含义不同，不能只按相似拼写替换。
- 检查成分残缺、搭配不当、主语中途变化、重复成分和句式杂糅。例如“软件由某人编写，并仍然负责维护”应明确谁负责维护。
- 增减倍数必须写清增量或最终值，详见[数字规则](numbers-and-punctuation.md)。
- 已配置的 Markdownlint、Code Spell Checker、LanguageTool 或 Vale 可辅助检查。只运行当前环境实际可用的工具，不为普通润色强制安装依赖；工具检查不能证明技术内容正确。
